# R&D 특구 유사 과제 검색 프로토타입 — 설계 문서

- 상태: 승인 대기 (사용자 검토 전)
- 작성일: 2026-08-21 (개정 1: service-planner/security-lead/qa-verifier 3자 검토 반영)
- 개정 2: 2026-08-21 — 실제 데이터 확인 후 **연구자 추천** 기능 추가, 조인 결과 실측치 반영
- 산출물 단계: 1단계(Jupyter 노트북). 결과가 괜찮으면 2단계(정적 HTML)로 확장.

## 1. 배경

공공데이터포털에서 연구개발특구진흥재단이 제공하는 데이터를 조사한 결과, 개별 "과제" 단위의
분야/키워드 정보를 가진 데이터셋은 없었다(기업 목록, 지역 정보, 지구별 집계 통계뿐). 대신
한국연구재단이 제공하는 `이알앤디_과제정보`(과제명 포함, 11,788건)를 결합해서, "R&D 특구 소속
기관이 수행한 과제"만 추출해 활용하기로 했다.

## 2. 페르소나 & 핵심 니즈

**신규 과제를 기획하는 사람** — 자신이 준비 중인 주제와 비슷한 과제가 이미 있는지, 있다면 몇 건이고
어떤 기관이 수행했는지 확인하고 싶다.

사용자는 한 종류(주제를 입력하고 결과를 직접 조작·탐색하는 사람)로 한정한다. 발표 시연을 옆에서
지켜보는 관객은 별도 사용자로 설계하지 않는다(이 사용자가 조작하는 것을 보는 입장으로 정리).

## 4. 검색 방식 선택: TF-IDF 코사인 유사도

세 가지 방식(TF-IDF 코사인 유사도 / 키워드·카테고리 규칙 기반 필터 / 외부 LLM API 의미 판단)을
비교한 결과 TF-IDF 방식을 선택했다.

**선택 이유**: 화면2의 클러스터 지도에 필요한 TF-IDF 벡터화를 화면1의 검색과 **하나의 파이프라인으로
공유**할 수 있어 신규 의존성이 거의 없고(scikit-learn 하나로 벡터화·유사도·SVD·KMeans 전부 해결),
결과가 완전히 결정적이라 "왜 이 과제가 검색됐는지" 설명하기 쉽다. 개정 2의 연구자 추천도 같은 유사도
결과를 집계만 바꿔 재사용하므로 추가 모델이 필요 없다.

(주의: 이 문서를 쓰는 시점에 구현 코드는 아직 없다. "재사용"은 노트북 안에서 하나의 벡터화 결과를
세 용도(검색·클러스터링·연구자 집계)가 공유한다는 설계상의 의미이며, 기존에 검증된 코드가 존재한다는
뜻이 아니다.)

**알려진 한계**: 동의어/다른 표현(예: "인공지능" vs "AI")을 사용한 과제는 표면적 단어가 겹치지 않아
유사 과제로 잡히지 않을 수 있다. 이 한계는 인지하되, 임계값 튜닝이나 간단한 동의어 사전 정규화
정도로 완화 범위 내에서 다루고, 별도 인프라(LLM 등)를 새로 두지 않는다.

**기각한 대안**:
- 키워드/카테고리 규칙 기반 필터: "유사도" 개념 자체가 없어 페르소나의 질문("비슷한 과제 몇 건")에
  근본적으로 답하기 어렵고, 정확히 같은 단어를 안 쓰면 있는데도 0건으로 나와 신뢰를 깎아먹을 위험.
- 외부 LLM API 의미 판단: 전체 후보를 프롬프트에 넣을 수 없어 TF-IDF와 결합한 하이브리드가 필요해
  단독으로 성립하지 않고, API 키/네트워크/비결정성/응답 지연이 하루 프로토타입 범위를 넘어섬.

## 6. 화면 상세

### 화면 1 — 유사 과제 검색 (핵심)
- 입력: ipywidgets Text 위젯 + 검색 버튼 (자유 텍스트, 준비 중인 과제 주제). 버튼 클릭 시 셀
  재실행 없이 반복 검색 가능
- 출력:
  - 내 주제가 속한 것으로 추정되는 클러스터 번호 (화면2와 번호 대조 없이 바로 연결)
  - 유사 과제 건수 (임계값 이상인 것만 카운트)
  - 수행 기관 목록 (중복 제거)
  - 유사 과제 Top-N 표: 과제명 / 주관기관명 / 연도 / 유사도 점수 / 클러스터 번호
- **0건(임계값 미달) 처리**: 완전히 빈 화면을 띄우지 않는다. 임계값 이상인 결과가 없어도 유사도
  기준 상위 3건을 "참고용 — 임계값 미달" 라벨과 함께 Top-N 표 자리에 표시한다. 안내 문구는
  "정확히 일치하는 유사 과제를 찾지 못했습니다. 아래는 유사도가 가장 높았던 3건입니다(참고용)." 로
  고정한다. 진짜 빈 화면은 특구 소속 과제 자체가 0건인 극단적 경우(조인 결과가 비어 있는 경우)로만
  한정되며, 이 경우의 문구는 별도로 "특구 소속 기관이 수행한 과제 데이터가 없습니다."로 고정한다.

### 6.1 화면 1 내 연구자 추천 (개정 2 추가)

**왜 화면3을 만들지 않는가**: DESIGN_LOG.md의 범위 결정에 "화면 1~2개 범위를 벗어나지 않는 선에서만
고름"이 명시되어 있다. 화면3을 신설하면 그 제약이 깨지므로, 화면1의 기존 검색 버튼 하나로 유사 과제
표와 연구자 추천 표가 **함께 갱신**되는 구조로 붙인다. 위젯은 랭킹 드롭다운 1개만 늘어난다(Text +
버튼 + 드롭다운 = 3개). PROJECT_PLAN.md 8절의 위험 2번(ipywidgets 렌더링 실패)이 드롭다운에도 적용
되므로, 대체 방안도 동일하게 적용한다 — 위젯이 렌더링되지 않으면 랭킹 기준을 셀 상단 변수
(`rank_by = "최고유사도"`)로 지정하고 셀을 재실행한다.

**랭킹 기준 — 드롭다운으로 사용자가 전환** (`ipywidgets.Dropdown`)

| 선택지 | 정렬 방식 |
|---|---|
| 최고 유사도 (기본값) | 해당 연구자의 과제 중 최고 유사도 |
| 유사 과제 건수 | 임계값 이상 과제 수, 동점은 최고 유사도로 tie-break |
| 합산 점수 | 임계값 이상 과제 유사도의 합 |

기본값을 최고 유사도로 두는 이유: 매칭된 1,680건에서 연구자 1,464명 중 **1,272명(86.9%)이 과제
1건**이므로 세 방식의 결과가 대부분 동일하고, 1건짜리 연구자에게 가장 직관적으로 설명된다
(과제 2건 이상은 192명, 3건은 24명).

**집계 키는 `연구자번호` — 이름 기준 집계 금지**

이름으로 묶으면 안 되는 이유는 실측으로 확인됐다. 매칭 데이터에 **동명이인이 64건** 있고, 가장 심한
경우 한 이름이 서로 다른 연구자번호 **3개**에 걸쳐 있다(실제 값은 원본 CSV 참조 — 이 문서에는 실명과
식별번호를 기록하지 않는다). 이름으로 집계하면
서로 다른 3명이 "과제 3건을 수행한 1명"으로 합쳐지는데, 이 오류는 화면상 자연스러워 보여서 발표 중
발견이 불가능하다.

**표시 컬럼**: `연구책임자명 / 주관기관명 / 특구지역 / 대표 유사 과제명 / 유사도 / 과제수`

- **대표 유사 과제명**: 그 연구자의 과제 중 **입력 주제와 유사도가 가장 높은 과제 1건**의 과제명.
  랭킹 기준을 무엇으로 바꾸든 이 컬럼의 정의는 고정한다(건수·합산 기준으로 정렬해도 대표 과제는
  최고 유사도 과제).
- **유사도**: 위 대표 과제의 유사도 값. 합산 점수 기준으로 정렬한 경우에도 이 컬럼은 합산값이 아니라
  대표 과제의 유사도를 보여주고, 합산값은 정렬에만 쓴다(같은 컬럼에 다른 의미의 숫자가 들어가면
  발표 중 설명이 엉킨다).
- **과제수**: 그 연구자의 임계값 이상 과제 건수.

**동명이인 표기 규칙**: 이름+소속기관이 같은데 연구자번호가 다른 경우가 **11쌍** 있다(경북대·전북대·
전남대·충남대 등에 분포). 이 경우에만 이름 뒤에 연구자번호 뒷 4자리를 붙여 `홍길동(1234)` 형태로
구분한다. 중복이 없는 나머지 행은 번호 없이 표시한다 — 공개 데이터이지만 8자리 식별번호를 모든 행에
노출할 이유가 없으므로 구분이 필요한 곳에만 최소로 쓴다.

**0건 처리**: 화면1의 기존 원칙과 동일하게 빈 표를 띄우지 않는다. 임계값 이상 결과가 없으면 참고용
상위 3건에 해당하는 연구자를 `참고용 — 임계값 미달` 라벨과 함께 표시한다.

## 7. 구현 단계에서 결정할 파라미터 (지금 확정하지 않음)

- 코사인 유사도 임계값 (0건/참고용 판정 기준값)
- KMeans의 k값
- 동의어 정규화 사전의 범위(있다면)
- 연구자 추천 표의 Top-N 개수 (개정 2)

이 값들은 실제 데이터 분포를 보고 조정하는 것이 합리적이므로, 설계 단계에서 미리 고정하지 않고
구현 중 데이터를 보며 정한다. 단, **qa-verifier 검토에 따라 이 파라미터들은 구현 완료 후 최종
확정하고, 발표 리허설에서 실제 시연 문구로 미리 검증해야 하며, 발표 당일 라이브로 튜닝하지
않는다** — 그렇지 않으면 4장에서 선택 이유로 든 "결과가 결정적"이라는 근거가 무색해진다.

(보안과제여부 필터링, 0건 결과 화면 문구, 화면1의 클러스터 번호 표시 여부는 3자 검토를 거쳐
위 3·5·6장에 이미 확정 반영했으므로 이 목록에서 제외한다.)

**연구자 추천의 랭킹 드롭다운은 위 "라이브 튜닝 금지" 원칙의 예외가 아니다.** 드롭다운은 발표 중
결과를 바꿔가며 보여주기 위한 **의도된 기능**이고, 세 선택지의 계산식은 구현 시점에 고정된다. 반면 위
파라미터들은 결과의 판정 기준을 바꾸는 값이므로 발표 전에 확정한다. 즉 드롭다운 전환은 "같은 데이터를
다른 기준으로 보여주는 것"이고, 파라미터 튜닝은 "판정 자체를 바꾸는 것"이라는 점에서 구분된다.

## 8. 성공 기준

- 하루 안에 화면1(핵심 기능)까지 동작
- 화면1만으로 페르소나의 질문("비슷한 과제가 있는지, 몇 건인지, 어떤 기관인지")에 답할 수 있음
- 화면1과 화면2 모두에서 동일한 클러스터 번호가 표시되어, 육안 대조 없이 바로 연결 확인 가능
- 임계값 미달 시에도 완전히 빈 화면 없이 참고용 상위 3건이 표시됨
- 보안과제로 표시된 레코드가 화면1/화면2 어디에도 노출되지 않음
- 로그인/서버/DB 없이 노트북 단독 실행으로 재현 가능
- **연구자 추천(개정 2)**: 예시 주제 3개 각각에 연구자 추천 표가 1건 이상 표시되고, 랭킹 드롭다운
  3개 값을 모두 전환해도 에러가 나지 않음 (예시 3개 × 드롭다운 3개 = 9회 확인)
- **연구자 추천(개정 2)**: 집계가 `연구자번호` 기준으로 수행되어, 동명이인(한 이름이 연구자번호 3개에
  걸친 사례가 있음)이 한 명으로 합쳐지지 않음
