# 리뷰 요청 — 클러스터 라벨링/유사 이유 설명 기능 설계안

> 이 문서는 다른 세션(Claude)과 브레인스토밍한 내용을 정리한 것입니다. 현재 프로젝트(PROJECT_PLAN.md)에 이 설계를 그대로 반영해도 괜찮을지, 혹은 더 나은 대안이 있는지 검토해주세요.

## 배경

PROJECT_PLAN의 화면1(유사 과제 검색)·화면2(전체 클러스터 지도)에 "AI 활용" 요소를 얇게 얹고 싶었음. 다만 기존 계획에서 "LLM 기반 의미 검색/클러스터 라벨링"은 전체 11,788건을 프롬프트에 넣을 수 없어 하이브리드가 되어버린다는 이유로 범위 밖으로 이미 제외되어 있음. 이건 LLM이 **검색 엔진 자체**를 대체하는 경우에만 해당하는 제약이라고 보고, 검색은 그대로 TF-IDF+코사인 유사도(결정적)로 유지한 채, 그 위에 **설명/라벨링 레이어**만 얇게 추가하는 방향으로 조정함.

## 제안: 로컬 LLM과 HCX를 체이닝하지 않고 역할로 분리

처음엔 "로컬 LLM이 요약 → 중간 단계 → HCX가 설명"하는 체이닝 구조를 검토했으나, 다음 이유로 기각함.

- 라이브 데모 중 두 모델 호출이 순차로 다 성공해야 결과가 나와 실패 지점이 두 배가 됨
- 사용자가 입력하는 과제 주제는 이미 짧은 문장이라, 로컬 LLM 요약이 TF-IDF가 참조할 키워드를 오히려 줄여 검색 품질을 해칠 가능성이 있음

대신 아래처럼 **역할을 나눠 각각 독립적으로 배치**하는 안으로 조정함.

| 구분 | 로컬 LLM (llama.cpp, 1일차 실습) | HCX (2일차 실습) |
|---|---|---|
| 담당 기능 | 화면2 클러스터 라벨링 | 화면1 "왜 유사한가" 설명 |
| 실행 시점 | 개발 완료 후, 발표 전 1회 배치(오프라인) | 부분은 사전 캐싱, 부분은 라이브 |
| 발표 중 리스크 | 없음 (정적 파일만 읽음) | 예시 3문장은 캐시(리스크 없음), 임의 입력만 실시간 호출 + try/except 폴백 |

### 로컬 LLM — 클러스터 라벨링 상세

1. llama-server 실행 (한국어 지원 경량 GGUF 모델)
2. 클러스터(k개) 각각에서 중심에 가장 가까운 과제명 5~10개 추출
3. 프롬프트: "다음 과제명들의 공통 연구분야를 3단어 이내 한글로 요약해줘"
4. 결과를 `cluster_labels.json`(클러스터 번호 → 라벨)으로 저장
5. 화면2 코드는 이 JSON을 읽기만 함 — 발표 중 API/서버 호출 없음
6. 라벨이 이상하면 사후에 사람이 한 번 수정

### HCX — 유사 이유 설명 상세

1. 완료조건 1의 예시 문장 3개에 대해 미리 검색+HCX 설명을 받아 코드에 캐싱
2. 그 외 임의 입력은 실시간 HCX 호출, 실패 시 "설명 생성 실패, 아래는 유사 과제 목록입니다"로 폴백 (표는 항상 뜸)
3. 프롬프트: "사용자가 입력한 주제: {query}. 아래는 유사도가 높은 기존 과제 목록입니다: {Top-3 과제명}. 각 과제가 왜 유사한지 한 줄씩 설명해줘"

### 구현 우선순위 (1일 일정 기준)

1. 핵심 검색+지도 (기존 계획대로)
2. HCX 설명 (화면1, 가시성 높음)
3. 로컬 LLM 라벨링 (화면2는 보조라 시간 남으면; 부담되면 라벨링도 HCX로 통일)

### 보고서용 서사

로컬 LLM은 사전 계산·무료·네트워크 불필요하지만 짧고 정형화된 요약에만 적합, HCX는 실시간 자연어 설명 품질이 안정적이지만 네트워크·키 필요. 1일차 T10(작은 모델이 잘하는 일과 못하는 일)에서 배운 내용을 실제로 검증해본 사례로 서술 가능.

## 참고: "실제 서비스"로 갈 때 고려할 점 (오늘 구현 대상 아님, 향후계획 섹션용)

- **안정성**: 재시도/타임아웃/서킷 브레이커, 실패율 로깅
- **비용 관리**: 질의 자체가 아니라 "Top-3 조합" 단위로 캐시 키를 잡아 중복 호출 최소화
- **보안**: API 키는 서버 환경변수/시크릿 매니저로, 사용자 입력 길이 제한 및 프롬프트 인젝션 방지
- **인프라**: 노트북 프로세스 → 백엔드/프론트 분리, 검색 결과는 즉시·설명은 비동기(progressive loading)
- **품질 관리**: 생성된 설명에 언급된 과제명이 실제 Top-3와 일치하는지 최소 가드레일, 사용자 피드백 루프

## 검토 요청 사항

1. 이 역할 분리 구조가 PROJECT_PLAN 5번(도구 배치), 6번(데이터), 7번(아키텍처) 표와 충돌 없이 자연스럽게 들어가는지
2. 1일 일정에서 로컬 LLM 라벨링까지 넣는 게 현실적인지, 아니면 HCX로 통일하고 서사만 남기는 게 나은지
3. 놓친 리스크나 더 나은 대안이 있는지
